原文:
<https://blog.cloudflare.com/unpacking-cloudflare-workers-cpu-performance-benchmarks/>

原文主要講述了 Cloudflare Workers 和 Vercel 在 CPU 性能方面的一些對比,
在應用上的重點是 React SSR 類應用的 TTFB 測試.

其中我認為的一些關鍵點是:

1. 函數計算的調度問題 (非 CPU 計算消耗).
2. Node.js 對 V8 調參導致的性能問題.
3. 代碼中處理 buffer 不當導致的內存佔用及後續 GC 的問題.
4. Node.js 的非 Web 標準化問題, 比如 Streams API.
5. Cloudflare Workers 團隊在解決自己問題的過程中如果發現了生態問題, 甚至竟品問題,
   也期望一併解決.

我們的核心業務均由函數計算承擔, 在此處有許多經驗. 函數計算中的幾大時間消耗為:

1. 調度時間
2. (可能) 冷啟動時間
3. 執行時間 (被計算為 CPU 消耗)

一般來說, "執行時間" 與函數計算無關. 函數計算需要重點考慮的, 是 "調度時間" 和
"冷啟動時間".

作為用戶, 一些配置會影響到調度時間, 比如使用什麼操作系統, 是否要接入 VPC 等.

想要優化冷啟動時間, 則應該將重點放在 "架構" 上. 一般來說, 解釋型語言的冷啟動時間會小很多.
比如函數計算一般使用 Python, JavaScript, 而不使用 Java.

另外一種優化就是 "預熱", 可以理解為提前啟動. 但是預熱是有成本開銷的,
並且我認為預熱是有悖於函數計算模式的. 我更傾向於減少冷啟動時間, 而不是預熱.

Cloudflare Workers 針對調度問題的優化, 是所有用戶樂於看到的. 加量不加價,
並且默認生效, 用戶無需任何額外配置.

Node.js 的非 Web 標準化問題, 就是我們幾年前選型 Deno, 而非 Node.js 的關鍵原因.
即便我們不是全棧團隊, 也希望在 JS 領域, 技術棧儘量統一, 減少不必要的消耗.
